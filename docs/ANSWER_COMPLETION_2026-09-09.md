# 中断后自动补答验收

新问题优先获得语音输出，旧问题自动在后台完成文字答案，展示在原问题下。用户不需要说“继续”。明确更正或取消才放弃旧问题；失败可单独重试。已经生成完整的语音回答直接展示原转写。该机制不自动重播旧语音，也不重放任务确认、记忆写入或工具操作。

## 实现与恢复

- `product/answer_jobs.py` 使用已有追加日志保存每个问题的回答义务，不增加数据库；默认两个并发 HTTP 请求，20 秒生成截止，前台 45 秒没有终态时转为文字补答。
- 保存原问题当时的提示词、检索证据、时钟、任务快照；补答使用独立 user 消息，避免把用户问题埋在 JSON 历史上下文里影响格式。
- 新输入尚在处理时暂缓补答，让更正先提交；等待有上限，断线遗留输入不会永久阻塞旧问题。迟到更正仍会取消对应答案。
- 任务重启重新排队，可能重新付费调用供应商。仅一次结果发布；不能保证供应商端旧请求未完成。
- 前端显示每个问题的排队、运行、耗时、请求 ID、失败与取消状态。断开实时连接仍通过 HTTP 获取补答状态，刷新不会丢失已受理任务。
- 补答只结束对应的普通对话工作项，不将物理任务和等待确认的操作标记完成。

## 失败与边界

首次完整 17 组验收为 13 组通过、4 组失败，原始产物完整保留于 `outputs/automatic-answer-acceptance-1/`。补答恢复组的测试错误及真实检索问题已修复并单独复验通过；其余三组仍有未解决失败，不能宣称全项目通过。

1. 补答早期格式失败：原问题在 JSON 中时生成中文数字和字面 `\\n`，不满足书面格式。改为独立 user 消息后通过；语音转写可能合法输出“八十一”，验收分别记录其内容正确性和阿拉伯数字格式，保留原文。
2. “停下，换个问题”真实返回 `stop-speaking` 与 `request-help`。后端原先压掉整轮回答。现在提示词要求保留新问题，协议层不允许有回答意图的复合控制被停止标签吞掉，纯停止仍保持安静。
3. 补答恢复第一次测试等待了记忆语音，但实际协议是文字 `memory_status` 回执。修正等待条件后又发现“包裹／取件码”与“包裹取件码”精确过滤不一致；已允许实体与属性的完整拼接，拒绝不同所有者，真实恢复复验通过。
4. 社交时间查询把“昨天讨论的前天的约定”的第二时间锚点错误设为相对讨论，漏掉目标记录。此前提示词已有规定，仍不能保证模型遵守。
5. 相对时间组首次写入路由超过 3 秒，降级保存原文，回答正确但时间索引缺失。严格证据结构验收失败，不能拿答案正确替代索引完整性。
6. 22 条 EgoLife 标注的报告重启组：日报完成、周报维持取消，月报输出在 JSON 字符串中截断，任务明确失败。浏览器的小样本三种报告通过不代表此组通过。

新机制确保已处理的问答不会仅因换话题而默默丢弃，但供应商失败、误解和遗漏仍可能发生。失败会显示并保留，不承诺每个问题一定得到正确答案。实时控制仍须等待或恢复处理；未完成的物理动作与外部副作用不能由文字补答代替。
