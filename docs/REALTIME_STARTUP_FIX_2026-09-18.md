# 实时启动超时与云端 50002 错误

## 已确认的现象

- 原前端等待 `ready` 的期限是 15 秒，超时即主动关闭 WebSocket。
- `.egoassist/server.log` 中，旧会话在 2026-09-18 00:28:12 发起连接，00:28:21.824 收到云端 `session created`。
- 会话 journal 在 00:28:35.090 记录 `context.replayed`（82 条），00:28:35.092 记录 `provider.session.ready`。从发起连接到就绪约 23 秒，超过浏览器期限。
- 该历史 journal 约 113 MB、5.2 万条事件。上下文消息投影单独测量约 53 ms；不能仅凭日志大小判断整个耗时来自文本处理。
- 工具恢复在 `set_context_harness` 与 `pending_tool_confirmations` 中三次无筛选复制完整日志，是已定位的额外本地启动开销。SDK 配置与历史发送也使用同步网络调用，原先在异步主循环中执行。

## 修复

- 工具恢复使用既有类型索引，仅复制工具事件；最近 512 条使用有界读取，保留原来的事件范围语义。
- SDK 配置与历史发送移至工作线程，并检查关闭和连接代次，避免旧连接恢复后重新置为在线。
- 向页面发送云端连接、历史恢复阶段。总等待有 60 秒上限，启动错误立即显示真实原因。
- 浏览器断开时，进度仍先持久化；发送进度遇到连接重置不会让分类任务异常退出。
- 原始历史和个人日记数据不删除、不迁移。

## 验证

- 189 项相关回归通过；增加云端错误提示测试后，另运行相关 67 项测试通过。最终涉及 190 个不同测试。
- 真实 Qwen 实时连接，使用旧会话副本恢复 84 条历史，未使用摄像头或麦克风。
- `outputs/realtime-startup-fix-20260918/result.json`：优化全日志复制前，桥接初始化至就绪 5439.9 ms。
- `outputs/realtime-startup-fix-20260918-r2/result.json`：优化后 350.1 ms，其中连接和历史发送阶段 253.6 ms；监测阶段最大主循环间隔 38.4 ms。
- 上述不是整页启动耗时，也不是稳定延迟保证。包含日志加载、业务恢复和真实摄像头采集的整个产品仍有其他开销。主循环采样在桥接初始化之后启动，不能用该采样值证明所有启动阶段都不阻塞。

## 用户提供的云端错误

事件 `event_OMTv2geMkDsfZI9MCKNLT` 在服务日志中的发生时间为 00:33:22.262：

```text
COMMON_ERROR
<50002> InternalError.Algo.ModelServingError: Internal Error calling model processing.
```

云端在 00:33:22.268 主动关闭 WebSocket，本地随后恢复连接，00:33:23.441 再次收到 `session created`。这证明连接恢复，不证明被中断的回答完成。该错误不能仅凭现有日志归因于 API Key、账户余额、摄像头或本地证据检索；云端内部原因需要供应商追踪。

原页面直接显示 Python 字典。现在显示“云端实时模型处理失败，本次回答可能中断，请重试。”，同时保留 `code`、`eventId`、原始错误消息和可重试标记供诊断。连接恢复继续使用现有机制；没有新增自动重复执行用户工具操作的逻辑。
