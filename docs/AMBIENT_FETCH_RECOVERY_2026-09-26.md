# 环境观察与状态同步断线恢复

2026-09-26，用户报告“后台环境观察 Failed to fetch”和“状态更新中断”。排查时本地 8770 在线，认证检查返回 200，日志显示当前会话状态接口持续返回 200。无法仅凭这些证据确定最初网络错误的触发原因，但代码确认两处恢复缺陷：轮询成功后没有清掉之前写入对话栏的连接错误；观察控制请求响应丢失后，没有核对实际是否已生效。

## 修改后的行为

- 状态连接提示独立显示，收到有效的当前会话状态后清除，不覆盖文字发送或模型回复的错误。晚到的失败不会覆盖更新的成功状态，切换账号/会话后也不再写入原请求错误。
- 网络错误使用中文说明；HTTP 服务错误仍保留原错误及状态码。
- 观察设置、开启和停止遇到网络错误或超时时，等待后续状态核对。已生效则显示确认；未确认则保留草稿并提示核对后重试，不自动重放写请求。
- 用户继续编辑草稿时撤销旧设置操作的待确认状态，避免恢复后覆盖新编辑。
- 浏览器网络恢复事件立即触发状态查询；常规轮询仍保持单次在途请求及原超时限制。
- 更新脚本版本号，刷新页面即可加载；此次无需服务重启。

## 验证

6 项请求与观察接口测试通过；3 个修改的 JavaScript 文件语法检查通过。

在本地 8770 的隔离账号上，真实 Edge 浏览器验证通过：注入状态网络中断、保存请求未发出、保存响应在服务提交后丢失、停止响应在服务提交后丢失。确认连接提示恢复、对话错误不被覆盖、草稿保留、服务器结果核对、反复停止/开启及刷新持久化。原有 HTTP 503、旧快照、桌面/手机布局检查也通过，无页面异常。

本次验证不调用模型、不打开摄像头或麦克风；测试对象是浏览器到本地服务的控制与恢复，不是视觉模型识别质量。证据保存在 `outputs/ambient-fetch-20260926/acceptance.json`、`outputs/ambient-fetch-tests.log`。

另外观察到原会话 `/api/state` 响应约 2.26 MB；本次未将其判定为网络错误根因，也未更改状态负载结构。
